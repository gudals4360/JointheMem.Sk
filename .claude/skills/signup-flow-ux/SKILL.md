# 회원가입 플로우 UX 재사용 가이드

신세계면세점 회원가입 개선 작업에서 검증된 패턴을 다른 프로젝트에 옮겨 쓰기 위한 스킬. 브랜드·컬러·카피는 프로젝트마다 바꾸고, **구조·상태 설계·작업 방식**은 그대로 가져간다.

## 0. 시작 전 확인 (바꿀 것 vs 유지할 것)

| 바꿀 것 (프로젝트별) | 유지할 것 (재사용) |
|---|---|
| 디자인 토큰(컬러·폰트·라운드), 로고, 카피 | 화면 5단계 구조, 라우팅 방식 |
| 지원하는 SNS/인증 수단 | 이메일 상태 머신, 비밀번호 체크리스트 |
| 약관 항목·법적 문구 | 약관 전체동의 + 개별 펼침 구조 |
| 서버 API 응답 형식 | API 연결 지점(`config` 훅) 분리 |

디자인 시스템 문서(예: `gs-shop.md`)가 있으면 **토큰만 CSS 변수로 옮기고**, 상대 브랜드 클래스명·로고는 쓰지 않는다.

## 1. 표준 화면 흐름

1. **가입 방식 (entry)**: 상단 혜택 안내 → (선택) 일러스트 스와이프 → 주 가입 버튼 1개 → 간편가입은 **원형 아이콘 버튼 행** → 로그인 링크
2. **본인 인증 (verification)**: 인증 수단 선택, 진행 상태 표시
3. **정보 입력 (info)**: 이메일(중복 확인) · 비밀번호(규칙 체크리스트) · 이름/휴대폰(인증값 자동 채움) · 주소 등
4. **약관 동의 (consent)**: 전체 동의 + 필수/선택 개별 항목
5. **완료 (done)**: 환영 + 다음 행동(쇼핑/설정) 버튼

원칙:
- 화면당 **주 행동 1개**. 보조 행동은 시각적으로 낮춘다.
- 입력은 단계별로 쪼개고, 이미 아는 값(인증된 이름·번호)은 다시 묻지 않는다.
- 버튼과 설명 캡션은 **12px 이내로 붙여** 그룹으로 읽히게 한다(떨어져 있으면 별개 요소로 인식).
- SNS 가입은 텍스트 긴 버튼 나열 대신 **원형 아이콘 + 짧은 라벨**.

## 2. 단일 HTML 프로토타입 구조

외부 UI 라이브러리 없이 `index.html` 하나로 만든다(폰트 CDN 정도만 예외).

```js
const SCREENS = ["entry","verification","info","consent","done"];
function show(n){ /* SCREENS 순회하며 hidden 토글 */ }
function go(n){ show(n); history.pushState({n}, "", "#"+n); }
addEventListener("popstate", e => show(e.state?.n ?? "entry"));
// [data-go="info"] 클릭 → go, [data-back] 클릭 → history.back()
```

- 화면은 `<section id="v-{name}" hidden>`. 숨김 CSS는 `[hidden]{display:none!important}`로 보강(화면별 display 지정이 hidden을 덮는 사고 방지).
- 뒤로가기 = 브라우저 뒤로가기와 일치하도록 `pushState/popstate` 사용.
- 디버깅용: 콘솔에서 `go('info')`로 바로 점프.

## 3. 팀원 코드 병합 시 CSS/JS 충돌 방지

여러 사람이 만든 화면을 한 파일로 합칠 때:
- 화면마다 **고유 스코프 클래스/접두어**를 부여(`.ev`, `#v-info` + `si-`, `.cs`). 전역 셀렉터(`.content`, `.caption`, `button`)는 쓰지 않는다.
- 같은 이름이 겹치면 **더 구체적인 셀렉터로 덮지 말고** 먼저 스코프로 분리. 부득이 덮어야 하면 `#v-entry .content .caption`처럼 화면 id부터 시작.
- 레거시 화면을 보존해야 하면 `.cs`(신) / `.cs-old`(구)처럼 **복제 분리**하고 합치지 않는다.
- JS는 화면별 IIFE로 감싸 전역 오염을 막고, 화면 간 통신은 `CustomEvent`(예: `shin:info-complete`)로.
- 병합 후 검증: 각 화면을 375px에서 열어 간격·폰트가 병합 전과 같은지 `getBoundingClientRect()`로 실측.

## 4. 이메일 확인 상태 머신 (재가입 대응 포함)

단순 "중복/사용가능" 이진 판정 대신 상태를 나눈다.

```
idle → invalid(형식 오류) → checking → available | rejoin_available | unavailable
```

```js
const config = {
  // 프로토타입 목업. 실서비스에서는 이 함수만 서버 호출로 교체.
  checkEmail(email){ return new Promise(r => setTimeout(() => {
    const id = email.split('@')[0].toLowerCase();
    r(id.startsWith('rejoin') ? 'rejoin_available'
      : id.startsWith('blocked') ? 'unavailable' : 'available');
  }, 700)); }
};
```

- 상태: `emailState = {status, checked, token, failed}`. 값이 바뀌면 `checked=false`로 되돌리고 **확인 완료를 무효화**.
- 연속 입력 시 오래된 응답 무시: 요청마다 `token` 증가, 응답 도착 시 `token` 불일치면 버림.
- 가입 가능 조건 `isComplete()`에 `emailOk()`(available 또는 rejoin_available) 포함.
- 버튼 라벨: `이메일 확인` → `확인 중` → `확인 완료` → (수정 시) `다시 입력`.
- 메시지는 비난·기술 용어 없이, **다음 행동을 알려주는 문장**:
  - 사용 가능 / 이전에 사용한 이메일이에요. 다시 가입할 수 있어요 / 현재 이 이메일로 가입할 수 없어요. 다른 이메일을 사용해 주세요.
- ⚠️ 정책: 탈퇴·제재 사유 등 **내부 사유를 노출하지 않는다**. 계정 존재 여부 노출(계정 열거) 위험은 서버 정책과 함께 검토.

## 5. 비밀번호 / 입력 UX

- 규칙은 제출 후 에러가 아니라 **입력 중 체크리스트**로 실시간 표시(길이·영문·숫자·특수문자). 충족 시 색+아이콘으로 변화(색만 쓰지 않는다).
- 보기/숨기기 토글, `autocomplete="new-password"`, `inputmode`(숫자/이메일) 지정.
- 에러는 필드 하단에 한 줄, `aria-live="polite"`로 안내. 필드 `aria-describedby` 연결.

## 6. 약관 동의

- **전체 동의** 체크가 개별 항목을 일괄 토글, 개별이 모두 체크되면 전체 동의도 자동 체크.
- 필수/선택 구분 라벨, 상세 보기는 펼침(아코디언) 또는 바텀시트.
- 필수 항목 미충족 시 다음 버튼 비활성 + 이유 안내.
- 마케팅 수신 등 선택 동의는 기본 해제, 채널별 분리.

## 7. 일러스트 스와이프 (선택 요소)

- flex 트랙 + `scroll-snap-type:x mandatory`, 슬라이드 `scroll-snap-stop:always`, 양끝 스페이서로 가운데 정렬. 자동재생 없음(스와이프 전용).
- 슬라이드 간격은 좁게(카드 폭 대비 좁은 gap), 슬라이드 폭 약 37%.
- 마우스 드래그 대응은 pointer 이벤트(임계 40px). 인디케이터가 필요하면 `go(i)` 호출 시 직접 갱신(스크롤 이벤트 의존 금지).
- `position:relative` 트랙으로 `offsetLeft` 기준을 고정.

## 8. 접근성 · 반응형 체크리스트

- 터치 타깃 ≥ 44×44px, 포커스 링 제거 금지.
- 대비비 4.5:1 이상(텍스트), 상태는 색+텍스트/아이콘 병행.
- 아이콘 버튼은 `aria-label` 필수(원형 SNS 버튼 포함).
- 기준 뷰포트 375×812, 360px에서도 가로 스크롤 없음.
- `prefers-reduced-motion`에서 전환 애니메이션 최소화.

## 9. 작업·검증 절차

1. 요구사항 → 화면 단계 매핑, 유지/교체 항목 표(0장) 작성.
2. 레퍼런스 조사(예: UIbowl)는 **비슷한 유형 3~5개**만 보고 공통 패턴을 뽑아 적용.
3. 구현 후 로컬 서버(`python3 -m http.server`)로 열어 375px에서 확인. `file://`은 폰트/스크립트가 깨질 수 있어 피한다.
4. 상태 검증: 이메일 `rejoin…`/`blocked…` 입력, 약관 전체/개별 토글, 뒤로가기 순서.
5. 간격·정렬은 눈대중 말고 `getBoundingClientRect()`로 px 확인.

## 10. Git 작업 규칙

- 커밋·푸시는 **사용자가 요청할 때만**.
- 브랜치 이동 전 `git stash`, 이동 후 `pop`.
- main 푸시 전 `git pull --rebase`(여러 세션이 동시에 푸시).
- "main에 적용" 요청은 **해당 화면 변경만** 옮긴다. 디자인 개편 브랜치 전체를 병합하지 않는다.
- 전체 UI 개편 실험은 별도 브랜치(`redesign/...`)에서, 마음에 안 들면 `git revert`로 되돌린다.

## 11. 흔한 실수

- 병합 후 한 화면 스타일이 다른 화면 간격을 깨뜨림 → 3장 스코프 규칙.
- `hidden`이 `display` 지정에 덮여 화면이 겹쳐 보임 → 2장 보강 CSS.
- 이메일 확인 후 값을 수정했는데도 완료 상태 유지 → 4장 `checked` 무효화.
- 오래된 비동기 응답이 최신 입력 상태를 덮어씀 → 4장 `token` 비교.
- 외부 서비스 로고/클래스명을 그대로 가져옴 → 브랜드 자산은 프로젝트 것만 사용.

## 12. 이 스킬을 확장하는 법

새 프로젝트에서 발견한 패턴(다른 인증 수단, 새 약관 구조 등)은 해당 장에 추가하고, 프로젝트 고유 값은 넣지 않는다. 프로젝트 전용 규칙(화면 id, 파일 구조, 팀 브랜치 이름)은 그 저장소의 `.claude/skills/`에 별도 스킬로 둔다 (예: `shin-dutyfree-signup`).
